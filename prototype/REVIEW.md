# Span Electron 评审细则

评审从一个用户动作开始，以用户能看到的结果结束。例如，用户在 SSH 会话里拒绝一条命令，只有发起请求的远端回合应收到拒绝，输入框随后应恢复到正确状态。工厂、IPC、Rust 服务和界面都要围绕这条路径检查。构建、性能验证和发布沿用[仓库约定](../AGENTS.md)。

## 一轮评审怎么做

1. **选题。** 每轮从上轮遗留问题、用户反馈、失败的 CI 或最近改动中，选择影响最大的一条路径。修复优先级相同时，先处理影响已有会话或两个平台的缺陷。没有已知缺陷时，从下表选近期缺少证据的一项。
2. **定位。** 固定基线提交、候选改动、平台、后端、主机和最小数据集。记录触发步骤、预期、实际和用户影响。偶发问题保留慢样本或事件顺序；仅有怀疑时记为“待复现”。
3. **修复。** 已确认且属于本轮范围的问题直接修。沿正常入口做最小改动，保留旧会话和既有调用行为。已有测试漏掉这条失败路径时，补能在修复前失败、修复后通过的断言。
4. **复验。** 在相同条件下重跑原场景，再选一个最可能受影响的相邻场景。例如，修复失效 socket 的回退后，再验证有效共享后台仍能复用，退出 Span 后共享进程仍存活。凡是改变可见内容、布局或状态切换的改动，同时完成下文的美学评审。
5. **收尾和续轮。** 按条记录“已验证”“已修待验证”或“待复现”，附提交或差异、证据和剩余环境。仍有高优先级问题时继续下一轮；只剩外部验证时写明需要哪台机器、哪个安装包以及判定结果的操作。没有可复现问题且相关检查通过时，可以结束本轮。

## 问题优先级

| 级别 | 判定示例 | 处理方式 |
| --- | --- | --- |
| P0 | 审批交给了错误的主机或回合、未经用户选择执行特权操作、已保存的会话数据丢失 | 立即中断低优先级工作，阻止受影响版本交付，优先恢复正确行为并验证影响范围 |
| P1 | 支持的平台启动失败、已有会话无法继续、断线重连导致重复发送、长会话卡到无法输入 | 优先于新功能修复，用受影响平台或后端复验 |
| P2 | 阅读历史时被拉回底部、工具详情抢过最终答复、缩进使同级事件看似从属、键盘无法到达常用操作、有证据的性能回退 | 纳入对应交互或性能修复，同时验证相邻操作；影响扩大时上调级别 |
| P3 | 已有可用入口的重复按钮、次要间距或措辞不一致、局部维护成本 | 随相关区域优化，保留能说明改善的对照 |

## 美学评审

Span 是需要长时间阅读的桌面工作台。完成一轮任务时，视觉重心应回到答复；等待审批时，重心应移到待决定的操作和影响范围。同样的工具卡片，在运行中可以显眼，完成后应让出位置。评审时先说出**这个状态下，用户第一眼应该看到什么**，再看画面实际把目光引向哪里。

| 观察什么 | 在 Span 里怎样判断 |
| --- | --- |
| 主次与构图 | 把整窗截图缩小到刚好读不清文字，观察最醒目的区域，再回到原尺寸找结论或待办。侧栏能交代当前位置，输入区能找到下一步，连续几条已完成的工具记录也能让读者一眼找到答复。 |
| 排版与阅读节奏 | 用一段包含中文、英文模型名、长路径、代码和两级列表的真实回复通读。正文适合连续阅读，标题和段间距标出转折，等宽字帮助辨认命令与路径。窄窗换行后，第二行仍对齐所属文字，列表还有足够行宽。 |
| 留白与分组 | 隐去图标和颜色，仅凭间距、对齐和缩进判断归属。命令与它的输出应比它与下一次工具调用更紧密。展开再收起摘要，后面的同级事件应回到同一条左边线，新一轮对话应看得出起点。 |
| 表面与视觉噪声 | 并排看正文、摘要、终端输出、表格和输入框。每层底色、边框、阴影都应能解释它围住了什么。尝试去掉其中一层；如果归属依然清楚、结论更醒目，就保留更简洁的版本。 |
| 色彩与一致性 | 对照选中、焦点、运行、失败和待审批状态。强调色应有稳定含义，失败或待决定的操作还要能从文字或形状辨认。换后端后，同类操作沿用同样的字重、图标尺度和控件位置。 |
| 动态观感 | 连续观察发送、流式输出、工具展开、任务完成和输入框恢复。留意按钮换位、边缘抖动、状态反复闪现，以及完成后仍吸引注意的动画。焦点转移应与用户当前需要做的事一致。 |

**取证方式。** 从空会话、工具密集的执行过程、待审批或失败、完成后的长答复中选受影响的状态。用相同会话数据、窗口尺寸、缩放比例、滚动位置和卡片展开状态并排比较前后截图；涉及空间分配时，加看窄窗或打开文件预览的画面。动态问题留短录屏。评审记录写清“目光先落在哪里、靠什么区分层级、改后哪一点改善或变差”，并给出保留、修改或撤回的决定。纯风格偏好可以记录为取舍；遮蔽结论、混淆归属或掩盖审批风险的，按用户影响定级。

**会话视觉对照。** 在 1240 × 840 的模拟会话里，展开的摘要和命令曾使用同样宽的深灰底板，两块表面比最终答复更显眼。对照同一段会话后，历史摘要详情采用与标题对齐的内缩正文，命令保留等宽字与底板。两级列表仍能分辨，命令仍能从正文中快速找到。实时摘要用一行无底板的文字显示在目标卡片上方。检查 780 × 620 窗口时，滚回旧消息后摘要仍应可见，长文保留末端，换成新文字时行高和位置不变。目标卡片与输入框等宽，中间留出 7 CSS 像素。回合结束后，摘要以折叠卡片归入时间线的原位置，答复重新成为底部的主要内容。

**长答复的编辑排版。** 用一份包含三级标题、两级列表、内联路径、短结果表、长命令和引用的会话答复对照。先扫标题，再读每个项目的结果。常规标题用 22、17 和 15 CSS 像素建立层级，列表标记和缩进说明归属。短表使用内容所需的宽度，保留 Markdown 指定的列对齐。代码块用等宽字和独立底板，窄窗内可横向滚动。在 1240 × 840 检查整窗的视觉重心，在 740 × 520 分别检查答复开头和结尾。记录正文首先读到哪里，以及表格数值能否顺势读到对应的项目。[打包测试](test/smoke.mjs)

**任务计划视觉对照。** 执行中默认展开当前回合的结构化计划，用勾、实心点和空心圆区分已完成、进行中和等待中的步骤。核对宽窄窗口下的文字换行和对齐，长清单在卡片内滚动。回合结束后默认收起步骤，摘要保留实际完成数，较早的计划按需展开。用户主动展开、键盘还在计划正文里、已选中正文或正在历史中阅读可见计划时，保留展开状态。用连续两次进度更新检查手动折叠和展开，收起后检查列表已卸载，最终答复可直接阅读。[打包测试](test/smoke.mjs)

**会话目录视觉对照。** 工作区名称原先比其会话标题更靠右，长列表里分组和当前会话难以快速分辨。现在会话标题比工作区名称内缩 6 CSS 像素，组线沿文件夹图标的中心向下延伸。低对比的背景与细强调线标记当前打开的会话，键盘焦点用单独的细描边。滚动时把原有组标题固定在目录顶部，下一组到达时接替它。目录应在有多组和多页会话时复核，检查键盘焦点出现在标题下方，也要检查窄侧栏里长标题仍有足够空间。

**切换会话视觉对照。** 在已翻过多页历史的会话里展开命令卡片，停在卡片中间，再往返另一个会话。回来时核对首个可见块、它与视口顶边的距离和卡片展开状态。等待补回旧页时显示恢复提示，检查答复区没有先闪过顶部或最新消息。回到最新消息后重复往返，核对只打开最近一页。切走时只保留会话标识、阅读锚点和有限的展开记录，历史正文与卡片控件随原视图释放。[打包测试](test/catalog.mjs)

**输入区与草稿。** 在两个会话分别写入多行草稿后用侧栏往返，检查光标所在的输入区始终显示当前会话的内容。粘贴多行指令时，输入框按内容增高，超过可用会话高度的四分之一或 156 CSS 像素后在框内滚动。窄窗出现审批时，草稿区须先给审批、目标和至少一行历史留出空间。对照空输入、五行草稿和长粘贴，核对正在读的段落或最新消息仍在原来的阅读位置。使用相同会话 ID 的本机和 SSH 连接复查隔离。模拟请求延迟，分别在新会话编辑同样的文字、在原会话继续编辑和在空会话首次发送失败时核对草稿。重试成功后，时间线应只有一条用户消息，输入区清空。[目录验收](test/catalog.mjs) · [发送验收](test/smoke.mjs)

**审批视觉对照。** 长命令曾把决定按钮推出卡片的可见区。现在审批标题、主机和操作按钮始终可见，命令正文独立滚动。待审批的琥珀色边框和图标把注意力引到需要确认的操作，目标卡片保留原有位置。分支名收到标题栏，空间不足时优先保留会话标题，分支全名可悬停查看。在 740 × 520 窗口里同时打开终端、审批和长草稿，检查历史区至少有两行正文的高度，工作目录和按钮可以直接看到。缩小窗口时终端随窗口高度让出一部分空间，收到审批时终端高度保持稳定。[打包测试](test/smoke.mjs)

**扩展表单视觉对照。** 在 740 × 520 窗口执行 `/span-form` 后，让扩展依次显示确认和多行编辑。原先同一条指令同时出现在时间线和输入框，表单分隔线与输入框底板争夺注意力。发出的指令现在先归入时间线，输入框退到次要位置，表单靠题目、字段和提交按钮建立层次。核对可见的两行预填正文、焦点描边、按钮和历史位置。发送失败时检查原草稿恢复，用户已输入新文字时保留新草稿。[打包测试](test/real-pi.mjs) · [发送验收](test/smoke.mjs)

**文件预览遇到审批。** 在 780 × 620 的原始画面里，右侧预览遮住了审批范围和按钮，左边露出的半列内容也难以阅读。窄窗预览现在占满工作区，键盘跳过被盖住的会话和终端。检查审批到达时输入框已有的焦点是否保持，焦点在暂收的文件预览里时是否移到审批卡片。处理完后从标题栏恢复同一份文件，核对滚动位置和键盘焦点。再用 Escape 关闭预览，确认焦点回到打开文件的位置。宽窗中检查审批和文件能否并排操作。

**差异卡片视觉对照。** 展开含多个文件的变更，在 740 × 520 窗口里先确认正在查看的路径，再读具体改动。文件头与段落标记使用同一颜色，新增和删除行保留补丁原有符号、空格与制表符。切换文件再返回时核对纵向与横向的阅读位置。用超过 1 万行的差异检查分页边界、结尾、完整复制和折叠后回收。基准记录同一视口中实际挂载的差异行数。打开应用核对差异、代码块和 `/copy` 的剪贴板内容，桌面端校验纯文本写入请求。[打包测试](test/patch-view.mjs)

**命令输出视觉对照。** 在 740 × 520 窗口中同时打开终端与失败命令，先核对命令、退出码和工作目录，再读输出。失败状态和退出码放在摘要行右侧，长命令让出横向空间。展开被截断或跨行的命令，检查缩进、续行、键盘焦点和复制到剪贴板的原文。命令名能在摘要里读全时，展开直接看工作目录和输出。长日志滚动和分页时检查正文阅读位置、页首和页尾的连续性，以及复制出的原文是否到达末尾。流式日志跨过长输出阈值时，核对输出区仍保有焦点和滚动位置。用同一条超过 256 KiB 的日志记录实际挂载量和完整行数，折叠后检查详情已卸载，最终答复仍能找到。[打包测试](test/output-view.mjs)

**连续工具活动视觉对照。** 用包含八项成功活动、一条失败命令、文件变更和最终答复的窄窗会话，检查问题、过程和结论能否在同一屏阅读。已结束回合中，同一代理和缩进层级连续四项及以上成功命令或工具调用合为一行。正文、失败和文件变更保留在原处。检查运行中每项活动都可查看，已在阅读或操作该回合的人在结束时保留原有位置。用键盘展开后，核对原始顺序、缩进和输出。折叠时成员行卸载，展开长组时仍按视口渲染。[打包测试](test/smoke.mjs)

**代理与团队视觉对照。** 在窄窗核对单个子代理的名称和状态、多个代理的失败提示，以及展开后逐个成员的状态和输出。卡片和 `/agents` 面板沿用同一行布局，直接从成员名称打开会话。用长名称、模型名和多行结果复核状态列对齐、换行、键盘焦点及目标会话。后端提供父代理、负责人或任务依赖时，核对每个字段都归到正确的人或任务。用先启动、后返回状态的两条事件检查稀疏更新能复用名称，普通流式正文沿用已构建的成员索引。[打包测试](test/smoke.mjs)

**代理状态与名单刷新。** 已结束回合里的运行或等待状态用低对比度的「当时」文字标出，面板继续显示最新状态。模拟名单请求尚未返回时收到一条新状态，核对新名单会更新其他成员，同时保留这条更新。并行发出两次刷新、关闭团队或切换会话后，检查迟到的响应不会恢复旧状态或已关闭的团队。[协议检查](test/agent-protocol.mjs)

## 按改动选择验收场景

| 评审面 | 操作与通过条件 |
| --- | --- |
| 连接与进程归属 | 在本机和 SSH 分别覆盖有效共享端点、缺失端点和失效端点。有效时走 proxy 并完成一轮对话，回退时只创建一份可用的独立服务。重连、重载和退出后，旧响应不会写入新连接，共享后台继续服务，Span 所有的进程、监听和未决请求得到清理。Windows 启动改动还需覆盖 PATH 中没有 CLI、从已注册 ChatGPT 安装包发现 CLI 的情形。 |
| Agent 工厂与原生能力 | 新后端按 Agent 类型和本机／SSH 位置创建适配器。用支持和缺少某项能力的两个适配器分别检查控件。模型、思考强度、Fast、目标、用量、追加和排队跟进各自匹配实际调用；子代理的父子关系、团队成员与任务归属可追踪。对照主分支走一遍旧 Codex 会话的打开、翻页、继续与中断。Claude Code、Pi 或 Clue 的可用性以对应适配器的真实往返为准。[适配协议](ui/agent-protocol.d.ts) |
| Pi 原生进程 | 分别在 Windows 本机、EL8 本机和 EL8 SSH 启动固定版本的 Pi。测试模型连续发出两条推理概要，再执行一个测试命令。核对固定摘要行、工具输出、用量和最终回复。通过 Pi 扩展调出确认与多行表单，在窄窗检查正文和按钮完整可见，取消仅结束本次请求。重启工作台后，按 Pi 会话目录重新打开并确认模型收到之前的答复。模拟分支历史和排队中断时另核对事件归属。[打包测试](test/real-pi.mjs) |
| 会话隔离与异步操作 | 在不同后端、不同主机构造相同原始会话 ID。切换会话后再交付上一页历史、审批结果、用量或预览，当前页仍显示自己的内容。检查连续发送、打断、拒绝和重试，用户消息只出现一次，失败后的草稿可继续使用。 |
| 时间线与卡片 | 回放“用户消息 → 推理摘要 → 回复前半段 → 工具调用 → 回复后半段”。同时验证实时流和重新打开后的记录。同一回合的多条摘要事件更新输入区上方的同一行。滚动查看历史时，检查状态行的位置、行高和正文阅读位置。展开后段落与嵌套列表可读，结束后摘要可在原事件位置展开。命令有退出状态，补丁能定位文件，子代理有归属，最终回复可以选择和复制。折叠详情时检查正文未挂载，展开后空结果、长输出和失败状态都可辨认。 |
| 桌面布局与可操作性 | 在常用窗口宽度和窄窗口下分别打开侧栏、终端及文件预览。检查正文与输入区对齐，目标卡片独立位于输入框上方，并可用键盘展开。改变窗口高度后，原本跟随最新消息的用户仍能看见最新内容，原本阅读历史的用户保留阅读位置。核对窗口按钮、长路径和中文换行。合并入口前，验证侧栏收起时还能完成原操作。视觉调整用相同窗口、内容和展开状态的前后截图复核。 |
| 长会话与资源回收 | 用户停在历史中部时持续追加文本，视口保持原处；在底部时继续跟随。靠近顶部加载多轮旧记录，期间持续输入，按首个可见内容和像素偏移核对阅读位置，同时核对游标、顺序和挂载行数。关闭会话、预览和终端后检查监听器、缓存、PTY 和子进程回收。 |
| 文件预览期间的流式会话 | 在窄窗开始长回复后打开文件预览并等回合结束，检查被盖住的回复是否停止更新 DOM。恢复会话时，在底部的用户直接看到完整回复，读旧内容的用户留在原位置。EL8 使用同一 runner、同一个服务和同一 CPU 交替运行基线与候选渲染器，记录渲染进程及其主线程 CPU 时间、回复 DOM 更新批次、布局次数和渲染进程 PSS。Windows 重跑两种阅读位置的功能验收。[基准场景](test/covered-transcript.mjs) |
| 正在阅读的长流式回复 | 在 800 × 640 窗口停在长回复开头，等相同的 40 次增量到达。检查正文更新批次和阅读锚点。靠近已排版段落的末尾应看到追加内容，跳到最新消息后检查末尾可见，完成后核对全文、链接和选区。EL8 固定 CPU、软件渲染、服务和窗口尺寸，交替运行基线与候选，记录渲染进程及主线程 CPU、PSS 和键盘输入到正确文字画面的 P95。先以两次真实输入确认帧订阅能捕获正确像素。[基准场景](test/long-reply.mjs) |
| 跟随最新的长流式回复 | 在同样的窗口跟随回复末尾，交替运行 160 次高频追加。长回复的普通追加最多每 80 毫秒提交一次排版，核对更新间隔和末尾可见性。修改前文、首次看到积压内容和回合结束时及时更新。用稍后到达的 Markdown 引用定义核对前文链接，Windows 重跑可见性和链接验收。EL8 分别记录输入事件到达、首个动画帧回调、Electron 帧订阅和 X11 桌面出现正确像素的时点。先通过插入和删除两个动作校准两种像素观测。[基准场景](test/long-reply.mjs) |
| 终端持续输出 | 用超过待确认窗口的本机命令验证 Windows ConPTY 和 EL8 PTY。分别暂停及恢复确认，检查待处理字节数、最终输出、关闭耗时和重新打开。旧终端的确认到达后，新终端的待处理窗口保持原样。 |
| Electron 权限边界 | 从主进程逐项核对预加载桥接接口、消息来源与允许的方法。用正常交互验证工作区内文件可预览、越界路径被拒绝、外链受协议约束。审批窗口显示所请求的操作与范围，允许、拒绝和重复提交都能得到明确结果。日志与截图使用可公开的测试数据。 |
| 可维护性与交付 | 后端专属报文的解析留在适配器，界面复用统一事件和卡片。检查新增分支是否覆盖错误返回、取消和清理。涉及安装或发布时，核对 EL8 RPM、原生 Windows 产物、版本与标签；分支产物用于验证，交付安装版按仓库的标签流程发布。 |

## 证据怎么取

- **协议与状态。** 在 `prototype/` 运行 `npm run check` 做轻量检查。核对具体断言覆盖了哪条失败路径。受控事件适合验证并发、交错和重复回包，真实后端往返用于验证传输及方法兼容性。[协议回归用例](test/agent-protocol.mjs) · [真实 Codex 连接用例](test/backend.sh)
- **桌面与安装。** 编译、打包和安装测试在 GitHub Actions 运行。记录候选提交、作业链接和产物。EL8 检查普通用户从 RPM 启动和沙箱。Windows 从待发布 ZIP 解压并比对文件，再从解压目录启动，验收 ConPTY、窗口操作和会话功能。Windows 商店版发现 CLI 的结论须注明实际安装布局和执行结果。[预览工作流](../.github/workflows/web-workbench-preview.yml) · [Electron 冒烟用例](test/smoke.mjs)
- **性能。** 对性能改动，固定尺寸、数据、CPU 限制和渲染环境，在同一 runner 上交替测基线与候选。判断本次 Electron 改动的收益时选用改动前的 Electron 提交；现有 EL8 基准还提供原生 Span 0.1.0 的参照。记录主进程与进程树 CPU、PSS、输入到正确画面的 P95、样本数和最长停顿。内存问题补充打开、关闭、回收后的 RSS 与 Private_Dirty，核对渲染进程的 JavaScript 堆和 DOM 节点变化。基准中的手动垃圾回收采样独立记录。先证明观测器捕获到正确画面，再比较延迟；结果落在运行波动范围时复测并保留原始数据。[原型基准](test/benchmark.py) · [终端压力用例](test/terminal-pressure.mjs)

## 首轮从哪里开始

先审 Windows 用户报告的启动路径。在已安装 ChatGPT、PATH 中没有 `codex.exe` 的环境启动 Span，记录命中的 CLI 路径、实际连接方式、能否发送首条消息，以及退出后的进程状态。这项结果直接决定用户能否使用整套界面。随后审共享连接所有权和跨主机审批隔离，再审长会话分页与流式渲染。
