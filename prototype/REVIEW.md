# Span Electron 评审细则

评审从一个用户动作开始，以用户能看到的结果结束。例如，用户在 SSH 会话里拒绝一条命令，只有发起请求的远端回合应收到拒绝，输入框随后应恢复到正确状态。工厂、IPC、Rust 服务和界面都要围绕这条路径检查。构建、性能验证和发布沿用[仓库约定](../AGENTS.md)。

## 一轮评审怎么做

1. **选题。** 每轮从上轮遗留问题、用户反馈、失败的 CI 或最近改动中，选择影响最大的一条路径。修复优先级相同时，先处理影响已有会话或两个平台的缺陷。没有已知缺陷时，从下表选近期缺少证据的一项。
2. **定位。** 固定基线提交、候选改动、平台、后端、主机和最小数据集。记录触发步骤、预期、实际和用户影响。界面问题按下文标记一个主要体验缺陷，说明用户具体在哪一步找不到入口、读错信息、无法操作或丢失位置。偶发问题保留慢样本或事件顺序；仅有怀疑时记为“待复现”。
3. **修复。** 已确认且属于本轮范围的问题直接修。沿正常入口做最小改动，保留旧会话和既有调用行为。已有测试漏掉这条失败路径时，补能在修复前失败、修复后通过的断言。
4. **复验。** 在相同条件下重跑原场景，再选一个最可能受影响的相邻场景。例如，修复失效 socket 的回退后，再验证有效共享后台仍能复用，退出 Span 后共享进程仍存活。凡是改变可见内容、布局或状态切换的改动，同时完成下文的美学评审。
5. **收尾和续轮。** 按条记录“已验证”“已修待验证”或“待复现”，附提交或差异、证据和剩余环境。仍有高优先级问题时继续下一轮；只剩外部验证时写明需要哪台机器、哪个安装包以及判定结果的操作。没有可复现问题且相关检查通过时，可以结束本轮。

## 问题优先级

| 级别 | 判定示例 | 处理方式 |
| --- | --- | --- |
| P0 | 审批交给了错误的主机或回合、未经用户选择执行特权操作、已保存的会话数据丢失 | 立即中断低优先级工作，阻止受影响版本交付，优先恢复正确行为并验证影响范围 |
| P1 | 支持的平台启动失败、已有会话无法继续、断线重连导致重复发送、长会话卡到无法输入 | 优先于新功能修复，用受影响平台或后端复验 |
| P2 | 阅读历史时被拉回底部、工具详情抢过最终答复、缩进使同级事件看似从属、键盘无法到达常用操作、有证据的性能回退 | 纳入对应交互或性能修复，同时验证相邻操作；影响扩大时上调级别 |
| P3 | 已有可用入口的重复按钮、次要间距或措辞不一致、局部维护成本 | 随相关区域优化，保留能说明改善的对照 |

## 用户体验缺陷

从用户眼前的画面和正在做的动作判断。先记下最直接的障碍，再追查造成它的界面行为。

| 缺陷 | 用户怎样遇到它 | 在 Span 里怎样复验 |
| --- | --- | --- |
| 入口难找 | 知道要做什么，却看不出该点哪里。常用入口藏在无标签图标、溢出菜单或收起的区域里。 | 在侧栏收起和窄窗两种状态下，分别找 Goal、用量和「最新消息」。记录首次正确操作前打开了哪些菜单。 |
| 操作费力 | 找到了入口，同一个意图仍要反复点击、切换焦点，或在多个看似等价的控件之间猜。 | 展开详情、返回输入区，再做一次编辑或取消。分别用鼠标和键盘检查多余步骤、重复入口的行为和关闭后的焦点。 |
| 视觉层级与可读性差 | 内容就在屏幕上，仍难以区分结论、过程和待处理事项。过重的卡片、密集的边框和含糊的缩进都会误导视线。 | 用一屏同时含答复、命令、失败提示和两级列表的会话，检查第一眼看到什么。核对缩进、留白、文字对比度和窄窗换行。 |
| 状态反馈不清 | 发出操作后，分不清消息已接收、正在运行、已排队、等待批准或失败。 | 逐个触发这些状态。检查固定推理行是否在原位更新，追加与排队是否有明确回执，失败是否说明影响及可以采取的下一步。 |
| 阅读或输入被打断 | 正在读旧消息或编辑草稿时，新内容把正文拉走、移动焦点，或打断选区。 | 停在一条旧消息上接收流式内容，再打开并关闭文件预览。核对原消息与像素偏移、草稿、选区和焦点。原先跟随最新消息时，检查末尾继续可见。 |
| 响应迟滞 | 操作本身清楚，键入、滚动或展开内容时，画面仍落后于手上的动作。 | 在长会话持续输出时分别键入、滚动和展开卡片。比较输入到正确画面的 P95 和最长停顿，同时记录 CPU 与 PSS。 |

固定推理行和 Goal 卡片用同一段流式会话验收。推理摘要在同一行持续更新，行高和位置保持稳定。Goal 独立位于输入框上方，展开和关闭后草稿、选区及阅读位置都能保留。Windows 与 EL8 都检查常用窗口和窄窗，静态层级留整窗截图，交互问题留短录屏或可重放的操作记录。

## 美学评审

Span 是需要长时间阅读的桌面工作台。完成一轮任务时，视觉重心应回到答复；等待审批时，重心应移到待决定的操作和影响范围。同样的工具卡片，在运行中可以显眼，完成后应让出位置。评审时先说出**这个状态下，用户第一眼应该看到什么**，再看画面实际把目光引向哪里。

| 观察什么 | 在 Span 里怎样判断 |
| --- | --- |
| 主次与构图 | 把整窗截图缩小到刚好读不清文字，观察最醒目的区域，再回到原尺寸找结论或待办。侧栏能交代当前位置，输入区能找到下一步，连续几条已完成的工具记录也能让读者一眼找到答复。 |
| 排版与阅读节奏 | 用一段包含中文、英文模型名、长路径、代码和两级列表的真实回复通读。正文适合连续阅读，标题和段间距标出转折，等宽字帮助辨认命令与路径。窄窗换行后，第二行仍对齐所属文字，列表还有足够行宽。 |
| 留白与分组 | 隐去图标和颜色，仅凭间距、对齐和缩进判断归属。命令与它的输出应比它与下一次工具调用更紧密。展开再收起摘要，后面的同级事件应回到同一条左边线，新一轮对话应看得出起点。 |
| 表面与视觉噪声 | 并排看正文、摘要、终端输出、表格和输入框。每层底色、边框、阴影都应能解释它围住了什么。尝试去掉其中一层；如果归属依然清楚、结论更醒目，就保留更简洁的版本。 |
| 色彩与一致性 | 对照选中、焦点、运行、失败和待审批状态。强调色应有稳定含义，失败或待决定的操作还要能从文字或形状辨认。换后端后，同类操作沿用同样的字重、图标尺度和控件位置。 |
| 动态观感 | 连续观察发送、流式输出、工具展开、任务完成和输入框恢复。留意按钮换位、边缘抖动、状态反复闪现，以及完成后仍吸引注意的动画。焦点转移应与用户当前需要做的事一致。 |

**取证方式。** 从空会话、工具密集的执行过程、待审批或失败、完成后的长答复中选受影响的状态。用相同会话数据、窗口尺寸、缩放比例、滚动位置和卡片展开状态并排比较前后截图；涉及空间分配时，加看窄窗或打开文件预览的画面。动态问题留短录屏。评审记录写清“目光先落在哪里、靠什么区分层级、改后哪一点改善或变差”，并给出保留、修改或撤回的决定。纯风格偏好可以记录为取舍；遮蔽结论、混淆归属或掩盖审批风险的，按用户影响定级。

**空白会话与输入框。** 在 1240 × 840 和 740 × 520 的窗口里分别查看空白会话、收到答复后的空输入框、有多行草稿的输入框。起稿时，标题和输入框组成居中的一组，宽窗内最多占 600 CSS 像素。收到答复后，输入框与正文左右对齐，空输入框给正文多留 18 CSS 像素。只有可发送的按钮使用强调色，停止按钮用方形图标单独辨认。确认多行草稿随内容增高，键盘焦点、阅读位置、实时推理行和 Goal 的顺序在状态切换后仍正确。[打包测试](test/smoke.mjs) · [草稿与阅读位置](test/catalog.mjs)

**Agent 菜单与运行设置。** 在 740 × 520 保留侧栏、终端和一段已选中的草稿，从工具栏和 `/model` 分别打开设置。菜单右缘与入口对齐，当前键盘项应先被看见。窄会话栏中设置面板沿正文两侧对齐，避免左边露出截断的文字。标签列随最长标签收窄，模型、思考强度、速度、模式和权限的值左缘排齐，在此尺寸可同时看到五项。用 Tab 进入控件，按 Escape 返回对应入口。核对草稿选区和阅读位置，组合输入期间的 Escape 只取消组字。[打包测试](test/smoke.mjs)

**技能目录。** 在 740 × 520 窗口分别用 `/skills` 和 Agent 菜单打开技能目录。核对技能名称、说明、来源和停用状态。用超过 30 项的目录查找最后一项，搜索覆盖完整目录，首屏只挂载 30 项。用键盘加载更多并按 Escape，核对焦点和原草稿。共享 Codex 切换工作区后，在发出首条消息前核对工作区技能。Pi 在本机和 SSH 均从自己的 RPC 读取技能，扩展命令仍可按原方式执行。[窄窗测试](test/smoke.mjs) · [真实 Codex](test/real-agent.mjs) · [真实 Pi](test/real-pi.mjs)

**OpenCode 与 Kilo 会话。** 分别用真实 CLI 在 Windows 本机、EL8 本机和 EL8 的 SSH 会话执行一轮。740 × 520 窗口里，推理文字更新时摘要行保持原位。审批标题说明操作类型，正文显示工作目录和命令原文，「仅允许这次」保留琥珀色强调。用 `/usage` 查看会话上下文及最近一次上报的 token 用量。重启后核对工具活动和答复仍按原顺序呈现并能继续发送，打开新会话时检查控件里的上一会话模型是否清除。用 `/plan` 往返规划与执行模式，核对 OpenCode 返回 `build`、Kilo 返回 `code`。[打包测试](test/real-acp.mjs)

**OpenCode 与 Kilo 委派。** 在上述三种环境里发起原生委派，让子代理查找一个用于验收的文件名。父会话显示后端上报的等待或运行状态。完成后用键盘打开子代理，核对任务、推理、工具输出和答复。父会话保留自己的答复和阅读位置。重启工作台后从原委派卡打开同一记录。协议检查另验证父子关系、分页顺序和关闭后丢弃迟到的结果。[打包测试](test/real-acp.mjs) · [协议检查](test/agent-protocol.mjs)

**Kilo 原生 Goal。** 在上述三个环境里用 `/goal` 新建目标。核对 740 × 520 窗口内固定推理行、目标卡片和输入框自上而下排列。目标运行时追加一条指令，当前模型步骤结束后先收到指令答复，再看原目标自动继续。推理摘要仍在原来的一行，Goal 保持「进行中」。暂停后退出工作台，再打开同一会话，检查卡片仍为「已暂停」，时间线仅展示后端标记为用户可见的内容。继续后由模型调用 `goal_report`，核对原生完成状态、原因和最终答复。清除后检查卡片收起。[打包测试](test/real-acp.mjs)

**本机附件。** 在 740 × 520 窗口用短文件名和一组同名前缀的长文件检查输入框。标签保留文件名末尾的编号和扩展名，悬停可看完整路径，键盘可移除并继续输入。标签最多显示两行，更多内容在标签区滚动。发送前切换会话，再切回核对草稿。模拟失败后核对文字和附件都可重试，收到回显后核对文件名只出现一次。重开 Pi 会话检查历史附件和正文的区分。Windows 与 EL8 使用原生文件选择，SSH 会话按后端位置隐藏本机文件入口。[Codex 打包测试](test/smoke.mjs) · [Pi 打包测试](test/real-pi.mjs)

**图片附件。** 在本机 Codex 选用已声明图片输入能力的模型，从同一个附件入口选择普通文件和 PNG。窄窗里核对图片图标、文件名、键盘移除和发送前后的附件顺序，模拟失败后检查两种附件仍保留。用真实 App Server 的测试网关确认收到图片输入，再重启工作台确认历史中保留图片标签。发送前如果更换为文本模型，保留原图片并提示切换模型或移除。[打包测试](test/smoke.mjs) · [真实 Codex](test/real-agent.mjs)

**图片预览。** 草稿和历史保留同一种紧凑附件标签，点击或按回车才读图。宽窗用侧边预览，窄窗沿用文件预览层，按比例容纳完整图片。在窄窗点「返回会话」后检查图片节点卸载、显示链接回收、原阅读位置保留。点「继续预览」后核对同一张图片和键盘焦点，按 Escape 回到附件并再次释放显示链接。重启后打开工作区外的历史图片时，通过系统选择器确认原文件，取消时保持原界面。图片预览读取上限为 4 MiB。[打包测试](test/smoke.mjs) · [真实 Codex](test/real-agent.mjs)

**粘贴截图。** 在支持图片的本机会话里用系统剪贴板粘贴 PNG。核对截图沿用现有标签，输入框保留光标和草稿，粘贴文本时仍执行普通文本粘贴。删除未发送的截图后检查文件回收，切换会话和重试后检查附件归属。只在明确发送时将截图交给 Agent。重启后从历史直接打开已发送截图。在 740 × 520 窗口观察附件区高度和可用正文空间。[打包测试](test/smoke.mjs) · [真实 Codex](test/real-agent.mjs)

**会话视觉对照。** 在 1240 × 840 的模拟会话里，核对完成后视线先落在最终答复，答复上方以低对比文字显示一行可展开的「任务过程」。展开后，过程说明采用与标题对齐的内缩正文，两级列表依然清楚，命令输出保留等宽字。实时进度用一行无底板的文字显示在目标卡片上方。检查 780 × 620 窗口时，滚回旧消息后实时进度仍应可见，长文保留末端，换成新文字时行高和位置不变。目标卡片与输入框等宽，中间留出 7 CSS 像素。

**会话滚动边缘。** 打开终端，再滚回历史，让滚动区边缘裁到一行正文。上下各用最多 14 CSS 像素过渡到工作区底色，避免残留笔画抢过摘要和 Goal。前后截图固定同一滚动位置和回合，核对渐变范围内的亮笔画变弱，滚动位置与点击命中保持一致。回到会话首尾后，检查首行与最终答复完整可读。键盘焦点进入正文或系统启用强制颜色时，边缘保持清晰。[打包测试](test/smoke.mjs)

**终端配色。** 在同一窗口用实际 PTY 输出对比错误、警告、成功、路径和追踪日志。错误红与警告黄要容易区分，次要日志用灰色降一级，路径和正文在深底上仍能直接读。记录这些样例的前景与底色，并检查低对比度 RGB 和反色样例，普通文字以 4.5∶1 为门槛。核对 Windows ConPTY 和 EL8 上的文字与配色，EL8 另看 WebGL 像素与回退到 DOM 后的同一行。[资源与回显用例](test/resource-isolation.mjs) · [桌面冒烟用例](test/smoke.mjs)

## 证据怎么取

- **协议与状态。** 在 `prototype/` 运行 `npm run check` 做轻量检查。核对具体断言覆盖了哪条失败路径。受控事件适合验证并发、交错和重复回包，真实后端往返用于验证传输及方法兼容性。[协议回归用例](test/agent-protocol.mjs) · [真实 Codex 连接用例](test/backend.sh)
- **桌面与安装。** 编译、打包和安装测试在 GitHub Actions 运行。记录候选提交、作业链接和产物。EL8 检查普通用户从 RPM 启动和沙箱。Windows 从待发布 ZIP 解压并比对文件，再从解压目录启动，验收 ConPTY、窗口操作和会话功能。Windows 商店版发现 CLI 的结论须注明实际安装布局和执行结果。[预览工作流](../.github/workflows/web-workbench-preview.yml) · [Electron 冒烟用例](test/smoke.mjs)
- **性能。** 对性能改动，固定尺寸、数据、CPU 限制和渲染环境，在同一 runner 上交替测基线与候选。判断本次 Electron 改动的收益时选用改动前的 Electron 提交；现有 EL8 基准还提供原生 Span 0.1.0 的参照。记录主进程与进程树 CPU、PSS、输入到正确画面的 P95、样本数和最长停顿。内存问题补充打开、关闭、回收后的 RSS 与 Private_Dirty，核对渲染进程的 JavaScript 堆和 DOM 节点变化。基准中的手动垃圾回收采样独立记录。先证明观测器捕获到正确画面，再比较延迟；结果落在运行波动范围时复测并保留原始数据。[原型基准](test/benchmark.py) · [终端压力用例](test/terminal-pressure.mjs)
- **终端与会话的资源归因。** 同一平台、同一安装产物和 880 × 640 初始窗口，每次从新进程载入同一份会话并打开空闲终端。以正序和逆序分别运行空闲、120 行定速终端输出、36 次会话滚动和 24 次窗口宽度重排。各场景核对输出末行、滚动距离或正文宽度。采样窗口至少 7.5 秒，记录实际长度。关闭终端后确认控件已卸载，分别记录关闭时、自然等待 2 秒和诊断回收后的数据。对照目前挂载的元素和 Chromium 的 DOM 节点总数，定位可以回收的分配。EL8 记录 PSS、RSS 和 Private_Dirty，Windows 记录工作集和专用内存。应用内调宽用来观察重排的分配量，原生拖拽延迟沿用独立的桌面测试。[资源归因用例](test/resource-isolation.mjs)
- **持续终端输出。** 在同一 runner 上使用同一套 Electron 和 PTY 服务，只替换候选与基线的界面，交替比较上面的 120 行用例，并记录实际更新的终端行数。先用鼠标双击选中文字，再单击清除，确认选区出现并消失。回显测试正序和逆序各跑一对，每次向实际终端发出 24 个间隔不同的按键。先取两种字符的像素参照，再用 Electron 帧订阅找到第一帧正确像素。另在渲染器内记录按键到 DOM 更新的时间，EL8 同时记录含回显的 PTY 数据到达时间。保留每次耗时与帧数。用两端截图复核末行的 ANSI 颜色、多字节字符和终端边界。EL8 还检查末行先于退出提示。两端关闭并重开终端，检查旧内容随面板释放。现有冒烟用例继续覆盖超过流控窗口的输出、EL8 SSH 和 WebGL 回退到 DOM。[资源与回显用例](test/resource-isolation.mjs) · [桌面冒烟用例](test/smoke.mjs)
- **终端持续输出时滚动会话。** EL8 在同一 runner 上交替运行同一个 Electron 包，比较工作台默认滚动和以 `--enable-smooth-scrolling` 启用 Chromium 滚动动画的表现。以相同的滚轮节奏、PTY 输出和滚动路径运行两组。用真实滚轮先校准稳定位置和正文像素，只在 X11 绘制通知到达后采样。分别记录首处像素变化、正确像素、滚动和动画帧的时间。保留未匹配的样本、截图采样数、窗口内的终端输出行数、渲染进程的 CPU 与 PSS，另记 Xvfb 的 CPU 时间。[X11 对照用例](test/benchmark.py)
- **终端收起时的持续输出。** 在 Windows 和 EL8 各自的同一 runner 上交替启动基线与候选。收起面板后生成超过 PTY 流控窗口的输出，核对输出仍在接收、终端网格保持原状。重新展开时检查最后两条输出的顺序及颜色，再输入命令确认是同一个 shell。分别记录收起期间的渲染进程 CPU 和内存、收到的字节数，以及展开到正确内容出现的时间。[资源验收](test/resource-isolation.mjs)
